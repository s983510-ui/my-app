> **요약**: 부재 담당자 앞으로 온 전화를 대신 받을 때, 접수·요약·물건 찾기를 도와 1건 처리 시간을 5분에서 2분 이하로 줄여요.

## 핵심 요약

| 관점 | 내용 |
|---|---|
| **문제** | 부재자 앞 전화를 하루 10건 이상, 건당 5분씩 대신 받고, 담당자에게는 회신 번호와 물건만 전달돼요 |
| **해결 방법** | 접수 화면 하나에서 부재 안내 → 고객 정보 입력 → 물건 후보 찾기 → AI 요약 → 저장까지 끝내고, 담당자는 자기 목록에서 봐요 |
| **기능·사용 효과** | 대신 받는 사람은 정해진 순서대로 빠르게 입력하고, 담당자는 복귀 후 경과를 바로 파악해요 |
| **핵심 가치** | 대리응대 시간 단축 + 전달 누락 0건 + 부재 사유 비공개 |

## 맥락 고정 (Context Anchor)

> Design·Do 문서에 그대로 이어 붙여서, 단계가 바뀌어도 목적을 잃지 않게 해요.

| 항목 | 내용 |
|---|---|
| **왜 (WHY)** | 부재 담당자 대리응대에 하루 약 1시간이 들고, 전달 정보가 부족해요 |
| **누가 (WHO)** | 대리응대자(전화를 대신 받는 직원), 담당자(복귀 후 처리하는 직원) |
| **가장 큰 위험 (RISK)** | AI가 없는 사실을 요약에 넣거나 목록에 없는 물건을 지어내는 것 / 공개 사이트에 실제 개인정보가 들어가는 것 |
| **성공 기준 (SUCCESS)** | 1건 2분 이하, 전달 5항목 빈칸 0, 요약 무수정 80%↑, 물건 후보 Top3 정답 80%↑ |
| **범위 (SCOPE)** | 1단계 기반·부재 안내 → 2단계 접수·요약·목록(must 1) → 3단계 물건 후보(must 2) → 4단계 측정 |

## 1. 개요

### 1.1 목적

부재 담당자의 전화를 대신 받는 직원이 한 화면에서 응대를 끝낼 수 있게 해요. 담당자가 돌아왔을 때 필요한 정보가 빠짐없이 남게 해요.

### 1.2 배경

PRD 1~2번 참고. 지금은 물건을 찾는 데 시간이 오래 걸리고, 메모가 부족해서 담당자가 다시 확인해야 해요.

### 1.3 관련 문서

- 기획서: [PRD.md](../../../PRD.md)
- 다음 문서: [설계서](../../02-design/features/absence-desk.design.md)

## 2. 범위

### 2.1 만들 것

- [ ] 샘플 데이터: 담당자 4명, 부재 일정, 물건 20건 (모두 가상)
- [ ] 담당자 선택과 부재 안내 문구
- [ ] 부재중 문의 접수 화면 + AI 요약 (must 1)
- [ ] 담당자별 문의 목록과 처리 완료 표시 (must 1)
- [ ] 물건 후보 찾기 (must 2)
- [ ] 성공 기준을 재는 기록과 간단한 지표 화면

### 2.2 만들지 않을 것

- 전화-전산 연동(CTI/PBX), 복무 시스템·메신저·k홉스 연동
- 실제 고객 정보·물건 데이터 사용
- 고객 본인 확인 절차 전산화 (안내 문구와 확인 체크만 넣어요)
- 사내 로그인(SSO), 통화 음성 자동 입력

## 3. 요구사항

### 3.1 기능 요구사항

| ID | 요구사항 | 기능 | 우선순위 | 상태 |
|---|---|---|---|---|
| FR-01 | 샘플 데이터(담당자·부재 일정·물건)를 넣고 불러와요 | 기반 | 높음 | 대기 |
| FR-02 | 담당자를 고르면 부재 안내 문구를 보여줘요. 형식은 "○○ 담당자는 ○월 ○일까지 부재 예정입니다"이고, 사유는 노출하지 않아요. AI 없이 규칙으로 만들어요 | 기반 | 높음 | 대기 |
| FR-03 | 접수 입력: 고객 성명, 휴대전화 뒷자리 4자리, 회신 번호, 고객이 말한 소재지, 문의 내용, "본인 확인함" 체크 | must 1 | 높음 | 대기 |
| FR-04 | 뒷자리는 숫자 4자리만 받고, 문의 내용에 전화번호 전체나 주민등록번호 형태가 있으면 경고해요 | must 1 | 높음 | 대기 |
| FR-05 | AI 요약: "고객 요청 / 확인된 사항 / 담당자가 할 일" 3줄로 정리해요. 입력에 없는 사실은 넣지 않고, 불확실하면 "확인 필요"로 써요 | must 1 | 높음 | 대기 |
| FR-06 | 요약을 사람이 고칠 수 있고, 고쳤는지 여부를 기록해요 | must 1 | 중간 | 대기 |
| FR-07 | 저장할 때 접수 화면을 연 시각과 저장 시각을 자동으로 기록해요 | must 1 | 높음 | 대기 |
| FR-08 | 담당자별 부재중 문의 목록: 미처리/처리 완료로 나눠 보여주고, "처리 완료"로 바꿀 수 있어요 | must 1 | 높음 | 대기 |
| FR-09 | 물건 후보 찾기: 고객이 말한 소재지·특징으로 그 담당자의 물건 목록에서 최대 3개 후보와 근거를 보여줘요. 없으면 "일치하는 물건이 없습니다"라고 해요 | must 2 | 높음 | 대기 |
| FR-10 | 후보를 고르면 접수 건에 물건이 연결돼요. 후보에 없으면 "물건 미확인"으로 저장할 수 있어요 | must 2 | 높음 | 대기 |
| FR-11 | 지표 화면: 평균 처리 시간, 하루 합계, 빈칸 있는 접수 수, 요약 수정 비율 | 측정 | 중간 | 대기 |
| FR-12 | 물건 후보 평가 스크립트: 샘플 문의 20건의 정답 물건이 Top3에 드는 비율 계산 | 측정 | 중간 | 대기 |

## 7. 구조 결정

### 7.1 프로젝트 수준

| 수준 | 특징 | 선택 |
|---|---|:---:|
| Starter | 단순 구조, 정적 사이트 | ☐ |
| **Dynamic** | 기능 단위 구성 + 외부 데이터 저장소 연동 | ☑ |
| Enterprise | 엄격한 계층 분리 | ☐ |

데이터를 여러 사람이 함께 보고 저장해야 해서 Dynamic을 골랐어요.

### 7.2 주요 결정

| 결정 | 후보 | 선택 | 이유 |
|---|---|---|---|
| 프레임워크 | Next.js | Next.js 16 (App Router) | 과정 고정 |
| 상태 관리 | React 기본 / Zustand | React 기본(useState) | 화면이 단순해요 |
| 서버 통신 | fetch / axios | fetch + Route Handler | 추가 설치 없이 돼요 (inu와 같은 방식) |
| 입력 폼 | 기본 / react-hook-form | 기본 폼 | 입력 칸이 적어요 |
| 디자인 | Tailwind | Tailwind | inu와 통일 |
| 시험 | Playwright | Playwright 시험 스크립트 | inu에서 쓰던 방식이고, Chrome 109 흉내 시험도 가능해요 |
| 데이터 저장 | Supabase / bkend.ai / 파일 | **Supabase** | 이미 계정이 있어요. bkit은 bkend.ai를 권하지만 Supabase로 대신해요 |
| AI | OpenAI | gpt-4o-mini | PRD 확정 |

### 7.3 폴더 구조 (예정)

```
app/              화면과 서버 API (Route Handler)
components/       화면 조각 (입력 폼, 목록, 후보 카드)
lib/              데이터베이스 연결, AI 호출, 규칙 함수
data/             샘플 데이터 (가상)
scripts/          시험·평가 스크립트
docs/             PDCA 문서 (01-plan, 02-design, 03-analysis, 04-report)
```
