## 맥락 고정 (Context Anchor)

> 계획서에서 그대로 가져왔어요.

| 항목 | 내용 |
|---|---|
| **왜 (WHY)** | 부재 담당자 대리응대에 하루 약 1시간이 들고, 전달 정보가 부족해요 |
| **누가 (WHO)** | 대리응대자(전화를 대신 받는 직원), 담당자(복귀 후 처리하는 직원) |
| **가장 큰 위험 (RISK)** | AI가 없는 사실을 요약에 넣거나 목록에 없는 물건을 지어내는 것 / 공개 사이트에 실제 개인정보가 들어가는 것 |
| **성공 기준 (SUCCESS)** | 1건 2분 이하, 전달 5항목 빈칸 0, 요약 무수정 80%↑, 물건 후보 Top3 정답 80%↑ |
| **범위 (SCOPE)** | 1단계 기반·부재 안내 → 2단계 접수·요약·목록(must 1) → 3단계 물건 후보(must 2) → 4단계 측정 |

## 1. 개요

### 1.1 설계 목표

- 대리응대자가 **한 화면에서 위에서 아래로** 채우기만 하면 응대가 끝나게 해요.
- AI는 **돕기만** 하고, 저장 전 최종 확인과 물건 선택은 사람이 해요.
- 개인정보는 **필요한 만큼만** 받고, AI에는 보내지 않아요.

### 1.2 설계 원칙

1. **최소 전송:** 고객 성명·뒷자리·회신 번호는 AI(OpenAI)로 보내지 않아요. AI에는 소재지 설명, 문의 내용, 물건 정보만 보내요.
2. **사유 비공개:** 부재 사유는 데이터베이스에만 있고, 서버 API가 화면으로 내보내지 않아요.
3. **AI 결과 재검사:** AI가 고른 물건 번호는 서버가 실제 목록과 대조해서, 없는 번호는 버려요.
4. **키는 서버에만:** 모든 키는 서버 코드에서만 읽어요.
5. **Chrome 109 호환:** 화면 코드에 최신 기능을 쓰지 않고, 색상은 일반 색상 코드(#hex)로만 써요.

## 2. 구조

### 2.0 구조 비교

| 기준 | A: 최소 | B: 깔끔 | C: 실용 |
|---|:-:|:-:|:-:|
| **방식** | 화면 파일 안에 다 넣기 | 계층을 엄격히 나누기 | 화면 / 서버 API / 공통 도구(lib) 3층 |
| **새 파일 수** | 약 8개 | 약 35개 | 약 22개 |
| **복잡도** | 낮음 | 높음 | 중간 |
| **유지보수** | 중간 | 높음 | 높음 |
| **추천 상황** | 급한 수정 | 장기 대형 프로젝트 | **기본 선택** |

**선택: C (실용)**. 실습 규모에 맞으면서, 데이터 저장소(Supabase ↔ 시험용 메모리)와 AI(실제 ↔ 시험용)를 바꿔 끼울 수 있어요.

### 2.1 구성도

```
┌──────────────┐   fetch    ┌──────────────────────┐        ┌──────────────┐
│  브라우저      │──────────▶│  Next.js 서버 (Vercel) │──────▶│  Supabase DB │
│  화면 3개      │◀──────────│  proxy.ts (접근 코드)   │        └──────────────┘
└──────────────┘            │  /api/* (Route Handler)│──────▶┌──────────────┐
                            │  lib/ (규칙·DB·AI)      │        │  OpenAI API  │
                            └──────────────────────┘        └──────────────┘
```

### 2.2 데이터 흐름 (접수 1건)

```
담당자 선택 → GET /api/staff (부재 안내 문구 포함)
  → 고객 정보 입력 (화면에서 형식 검사)
  → 소재지 입력 → POST /api/candidates → AI가 후보 고름 → 서버가 번호 재검사 → 후보 3개
  → 문의 내용 입력 → POST /api/summary → AI 3줄 요약 → 사람이 확인·수정
  → 저장 → POST /api/inquiries (서버에서 다시 검사, 시각 기록) → DB 저장
```

### 2.3 의존 관계

| 구성 요소 | 의존 대상 | 목적 |
|---|---|---|
| 화면(`app/*/page.tsx`) | `/api/*` | 데이터 읽기·쓰기 |
| `/api/*` | `lib/repo.ts`, `lib/ai.ts`, `lib/rules.ts` | 저장, AI, 규칙 |
| `lib/repo.ts` | Supabase (운영) / 메모리 저장소 (시험) | 데이터 저장 |
| `lib/ai.ts` | OpenAI (운영) / 시험용 응답 (시험) | 요약, 후보 |
| `proxy.ts` | `lib/access.ts` | 접근 코드 확인 |

## 3. 데이터 모델

### 3.1 표 정의

**staff (담당자)**

| 칸 | 형식 | 설명 |
|---|---|---|
| id | text, 기본키 | 예: `S01` |
| name | text | 가상 이름 |
| team | text | 예: 국유재산관리1팀 |
| region | text | 담당 지역 (예: 창녕군) |

**absences (부재 일정)**

| 칸 | 형식 | 설명 |
|---|---|---|
| id | bigint, 자동 증가 | |
| staff_id | text → staff.id | |
| start_date | date | 부재 시작일 |
| end_date | date | 부재 종료일 (이날까지 부재) |
| reason | text | 연차·교육·출장 등. **화면으로 절대 내보내지 않음** |

**properties (물건)**

| 칸 | 형식 | 설명 |
|---|---|---|
| id | text, 기본키 | 예: `P001` |
| staff_id | text → staff.id | 관리 담당자 |
| address | text | 소재지 (가상 지번) |
| land_category | text | 지목: 전·답·대·임야·도로 등 |
| area_m2 | numeric | 면적(㎡) |
| status | text | 대부중 / 미대부 / 매각 진행 |
| landmark | text | 주변 특징 (예: "○○초등학교 뒤편") |

**inquiries (부재중 문의)**

| 칸 | 형식 | 설명 |
|---|---|---|
| id | uuid, 기본키 | |
| staff_id | text → staff.id | 원래 담당자 |
| customer_name | text | 고객 성명 |
| phone_last4 | char(4) | 휴대전화 뒷자리 4자리 (숫자만) |
| callback_number | text | 회신 번호 |
| identity_checked | boolean | "본인 확인함" 체크 여부 |
| said_location | text | 고객이 말한 소재지 그대로 |
| property_id | text → properties.id, 빈 값 가능 | 연결한 물건. 비어 있으면 "물건 미확인" |
| content | text | 문의 내용 (대리응대자 입력) |
| summary_ai | text | AI가 처음 만든 요약 |
| summary | text | 최종 저장한 요약 |
| summary_edited | boolean | 사람이 요약을 고쳤는지 |
| opened_at | timestamptz | 접수 화면에서 담당자를 고른 시각 |
| saved_at | timestamptz | 저장 시각 |
| status | text | `open`(미처리) / `done`(처리 완료) |
| done_at | timestamptz, 빈 값 가능 | 처리 완료 시각 |

### 3.2 관계

```
staff 1 ──── N absences
staff 1 ──── N properties
staff 1 ──── N inquiries N ──── 0..1 properties
```

### 3.3 데이터베이스 설정 (Supabase)

- 위 4개 표를 만드는 SQL은 Do 단계에서 `supabase/schema.sql`로, 샘플 데이터는 `supabase/seed.sql`로 만들어요.
- 사용자가 Supabase 화면의 **SQL Editor**에 붙여넣고 실행해요.
- 4개 표 모두 **RLS(행 단위 보안)를 켜고 정책은 만들지 않아요.** 그러면 공개 키로는 아무것도 읽을 수 없어요. 서버만 비밀 키로 접근해요.
- 부재 일정 샘플은 `current_date` 기준으로 넣어요. 언제 실행해도 "지금 부재 중"인 담당자가 생겨요.

## 4. 서버 API

모든 `/api/*`는 접근 코드 쿠키가 있어야 해요. 없으면 `401`이에요. 예외는 `/api/session`이에요.

### 4.1 목록

| 메서드 | 주소 | 설명 | 요구사항 |
|---|---|---|---|
| POST | `/api/session` | 접근 코드 확인 → 쿠키 발급 | 접근 제한 |
| GET | `/api/staff` | 담당자 목록 + 부재 안내 문구 | FR-01, FR-02 |
| POST | `/api/candidates` | 물건 후보 최대 3개 | FR-09 |
| POST | `/api/summary` | 문의 3줄 요약 | FR-05 |
| POST | `/api/inquiries` | 접수 저장 | FR-03, FR-04, FR-06, FR-07, FR-10 |
| GET | `/api/inquiries?staffId=&status=` | 담당자별 문의 목록 | FR-08 |
| PATCH | `/api/inquiries/[id]` | 처리 완료로 변경 | FR-08 |
| GET | `/api/metrics` | 지표 | FR-11 |

### 4.2 상세

**`GET /api/staff`** → `200`

```json
{ "staff": [
  { "id": "S01", "name": "김가온", "team": "국유재산관리1팀", "region": "창녕군",
    "absentUntil": "2026-10-31",
    "notice": "김가온 담당자는 10월 31일까지 부재 예정입니다. 복귀 후 연락드리겠습니다." }
] }
```

- 부재 중이 아니면 `absentUntil: null`이고, 문구는 "김가온 담당자는 현재 근무 중입니다."예요.
- `reason`은 응답에 **들어가지 않아요**. 서버에서 조회할 때부터 이 칸을 고르지 않아요.
- 날짜는 한국 시간(Asia/Seoul) 기준이에요. 부재가 연달아 이어지면 마지막 종료일을 써요.

**`POST /api/candidates`**

- 요청: `{ "staffId": "S01", "saidLocation": "시장 뒤쪽 밭이라고 함" }`
- 응답 `200`: `{ "candidates": [{ "property": {…물건 정보}, "reason": "주소의 ○○리와 '시장' 특징이 일치" }] }`
- 일치하는 물건이 없으면 `candidates: []`, `message: "일치하는 물건이 없습니다"`예요.
- 처리 순서:
  1. 그 담당자의 물건만 조회해요.
  2. AI에 번호와 정보 목록을 보내요.
  3. AI는 JSON으로 답해요.
  4. **서버가 목록에 없는 번호를 버리고**, 최대 3개만 남겨요.

**`POST /api/summary`**

- 요청: `{ "content": "…", "saidLocation": "…", "propertyLabel": "P003 창녕군 ○○리 123 (전)" }`. 고객 이름이나 번호는 받지 않아요.
- 응답 `200`: `{ "summary": "고객 요청: …\n확인된 사항: …\n담당자가 할 일: …" }`
- 문의 내용에 전화번호 전체나 주민등록번호 형태가 있으면 `400`(`PERSONAL_INFO`)을 돌려줘요. AI로 보내지 않아요.

**`POST /api/inquiries`** → `201 { "id": "…", "elapsedSeconds": 95 }`

- 서버에서 다시 검사해요:
  - 뒷자리는 숫자 4자리
  - 회신 번호는 숫자와 하이픈(9~13자리)
  - 본인 확인 체크는 `true`
  - 문의·요약은 비어 있지 않고 개인정보 형태가 없어야 해요
  - `property_id`가 있으면 그 담당자의 물건이어야 해요
- `summary_edited`는 서버가 `summary !== summary_ai`로 계산해요.
- `saved_at`은 서버 시각으로 기록하고, `opened_at`은 화면이 보낸 값을 받아요.

**`GET /api/metrics`** → `200`

```json
{ "count": 12, "avgSeconds": 96, "todaySeconds": 610,
  "incompleteCount": 0, "editedRatio": 0.17 }
```

- `incompleteCount`는 전달 5항목(성명, 뒷자리, 물건 또는 "미확인" 표시, 요약, 회신 번호) 중 빈칸이 있는 건수예요.

## 6. AI 지시문

모델: `gpt-4o-mini`, 온도 0.1, JSON 형식으로 응답받아요.

### 6.1 요약 (`/api/summary`)

```
당신은 국유재산 담당 부서에서 부재 중인 동료에게 전화 문의를 전달하는 메모를 쓰는 직원입니다.
아래 [문의 내용]만 근거로 3가지를 한국어 존댓말 한 문장씩으로 쓰세요.
- request: 고객이 원하는 것
- confirmed: 통화에서 확인된 사실 (없으면 "확인 필요")
- todo: 담당자가 복귀 후 할 일
규칙:
1. [문의 내용]에 없는 사실(금액, 날짜, 약속, 법령)을 추가하지 마세요.
2. 불확실하면 "확인 필요"라고 쓰세요.
3. 전화번호, 주민등록번호, 고객 이름은 쓰지 마세요.
JSON으로만 답하세요: {"request": "...", "confirmed": "...", "todo": "..."}
```

서버가 세 줄을 "고객 요청: / 확인된 사항: / 담당자가 할 일:"로 붙여서 돌려줘요. 칸이 빠지면 "확인 필요"로 채워요.

### 6.2 물건 후보 (`/api/candidates`)

```
당신은 고객이 말한 위치 설명으로 국유재산 물건을 찾는 것을 돕습니다.
[물건 목록]에 있는 물건 중에서만, 고객 설명과 맞을 가능성이 높은 순서로 최대 3개를 고르세요.
각 후보에는 무엇이 일치하는지 근거(리·동 이름, 지번, 지목, 주변 특징)를 한 문장으로 쓰세요.
규칙:
1. [물건 목록]에 없는 번호를 만들지 마세요.
2. 일치하는 근거가 없으면 빈 목록을 주세요. 억지로 고르지 마세요.
JSON으로만 답하세요: {"candidates": [{"id": "P003", "reason": "..."}]}
```

## 7. 오류 처리

### 7.1 오류 코드

| 코드 | 상태 | 뜻 | 화면 문구 |
|---|:-:|---|---|
| `UNAUTHORIZED` | 401 | 접근 코드 없음/틀림 | 접근 코드가 맞지 않아요 |
| `VALIDATION` | 400 | 입력 형식 오류 | 칸별 안내 (예: 뒷자리는 숫자 4자리로 적어 주세요) |
| `PERSONAL_INFO` | 400 | 문의에 전화번호 전체·주민번호 형태 | 문의 내용에서 전화번호·주민등록번호를 지워 주세요 |
| `NOT_FOUND` | 404 | 없는 담당자·문의 | 찾을 수 없어요 |
| `AI_FAILED` | 502 | OpenAI 오류·시간 초과(15초) | AI 응답을 받지 못했어요. 직접 입력해 주세요 |
| `DB_FAILED` | 500 | DB 오류·설정 누락 | 저장하지 못했어요. 잠시 후 다시 시도해 주세요 |

AI가 실패해도 접수는 막지 않아요. 요약 칸에 직접 쓰고, 물건은 "미확인"으로 저장할 수 있어요.

### 7.2 오류 응답 형식

```json
{ "error": { "code": "VALIDATION", "message": "뒷자리는 숫자 4자리로 적어 주세요", "field": "phoneLast4" } }
```

## 8. 보안

- **접근 코드:**
  - `proxy.ts`가 `/login`과 `/api/session`을 뺀 모든 요청을 검사해요. Next.js 16에서는 `middleware` 대신 `proxy`를 써요.
  - `/api/session`이 `APP_ACCESS_CODE`와 비교해요. 맞으면 서명한 값을 `httpOnly`, `secure`, `sameSite=lax` 쿠키(12시간)로 줘요. 서명은 HMAC-SHA256이고 비밀값은 접근 코드예요.
  - 화면 요청은 `/login`으로 보내고, API 요청은 `401`을 돌려줘요.
- **비밀 값:** `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, `APP_ACCESS_CODE`는 서버에서만 읽어요(`server-only`).
- **DB:** RLS를 켜고 정책을 두지 않아요. 공개 키로는 접근할 수 없어요.
- **개인정보 최소화:** 뒷자리 4자리만 받아요. AI에는 성명·번호를 보내지 않아요. 문의 내용의 번호 형태는 막아요.
- **입력 길이 제한:** 성명 20자, 소재지 200자, 문의 2000자, 요약 600자예요.

## 9. 시험 계획

> Do 단계에서 기능을 만들 때 시험 코드도 함께 만들어요. Check 단계에서는 만든 시험을 돌리기만 해요.

### 9.1 시험 범위

| 종류 | 대상 | 도구 | 단계 |
|---|---|---|---|
| L1 API | 상태 코드, 입력 검사, 응답 모양 | Playwright request | Do |
| L2 화면 | 5.4 점검 목록의 요소가 있는지 | Playwright | Do |
| L3 시나리오 | 흐름 A → 흐름 B → 지표 | Playwright | Do |
| 호환성 | 같은 시나리오를 Chrome 109 흉내 브라우저로 | Playwright + 기능 제거 스크립트 | Do |
| 평가 | 물건 후보 Top3 정답률 | 평가 스크립트 + 정답 20건 | Check |

**시험 환경:** 이 작업 공간에서는 Supabase와 OpenAI에 직접 접속할 수 없어요. 그래서 시험할 때는 메모리 저장소와 시험용 AI 응답(`TEST_MODE=1`)으로 돌려요. 운영(Vercel)에서는 시험 모드를 쓰지 않아요. 운영에서 설정이 빠지면 조용히 넘어가지 않고 `DB_FAILED`로 알려요.
