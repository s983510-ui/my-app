## 1. 개요

### 1.1 설계 목표

- 세 사람(고객·대리응대자·담당자)이 **각자의 화면 하나**에서 자기 일을 끝내요.
- 정해진 규칙(부재 판단, 고객 찾기, 중복 합치기, 입력 검사)은 **AI 없이 프로그램 규칙**으로 처리해요. 그래야 결과가 매번 같고 시험할 수 있어요.
- AI는 **문의 3줄 요약 한 곳**에만 쓰고, 실패해도 업무가 멈추지 않게 해요.

### 1.2 설계 원칙

1. **Next.js만 사용:** 새 라이브러리를 넣지 않아요. 날짜 계산, 입력 검사, 쿠키 서명 모두 기본 기능으로 해요.
2. **최소 전송:** AI에는 문의 내용만 보내요.
3. **사유 비공개:** 부재 사유는 샘플 데이터에만 있고, 서버 API가 내보내는 값에서 아예 빼요.
4. **정확히 일치만 인정:** 고객 찾기는 정확히 일치할 때만 결과로 쳐요. 비슷한 이름은 찾지 않아요.
5. **Chrome 109 호환:** 색은 직접 정한 색상 코드로만, 화면 코드에는 최근 JavaScript 기능을 쓰지 않아요.

## 2. 구조

### 2.0 구조 비교

| 기준 | A: 최소 | B: 깔끔 | C: 실용 |
|---|:-:|:-:|:-:|
| **방식** | 화면 파일 안에 다 넣기 | 계층을 엄격히 나누기 | 화면 / 서버 API / 공통 도구(lib) 3층 |
| **새 파일 수** | 약 10개 | 약 45개 | 약 30개 |
| **복잡도** | 낮음 | 높음 | 중간 |
| **시험하기** | 어려움 (규칙이 화면에 섞임) | 쉬움 | 쉬움 (규칙이 lib에 모임) |
| **추천 상황** | 급한 수정 | 장기 대형 프로젝트 | **기본 선택** |

**선택: C (실용)**. 규칙 함수를 `lib/`에 모아 두면, 화면 없이도 규칙만 따로 시험할 수 있어요.

### 2.1 구성도

```
┌──────────────────┐  fetch   ┌───────────────────────────────┐        ┌────────────┐
│ 브라우저 화면 7개   │────────▶│ Next.js 서버 (Vercel)           │──────▶│ OpenAI API │
│ (/call /desk ...) │◀────────│  proxy.ts  : 접근 코드 검사       │ 요약만  └────────────┘
└──────────────────┘          │  app/api/* : 서버 API 9개        │
                              │  lib/      : 규칙·저장소·AI·접근  │
                              │  메모리 저장소 (샘플로 시작)       │
                              └───────────────────────────────┘
```

### 2.2 데이터 흐름

**흐름 A (고객, must 1)**
```
담당자 선택(이름/지역) → GET /api/staff → 부재 안내 문구(서버에서 계산)
  → [회신 받기] → POST /api/calls (선택 기록) → POST /api/tickets/callback (중복이면 합침)
  → [지금 통화] → POST /api/calls (선택 기록) → "직원에게 연결됩니다" → 대리응대자 화면으로
  → (부재 아님) → POST /api/calls → "담당자에게 연결됩니다"
```

**흐름 B (대리응대자, must 2)**
```
담당자 선택 → 이름 + 끝 4자리 → POST /api/lookup
  → 1명: 고객 + 물건(최대 5건)
  → 2명 이상 / 0명: 생년월일 6자리 입력 → POST /api/lookup (같은 lookupId) → 1명 / 담당자 확인 필요 / 고객 미확인
  → 문의 입력 → POST /api/summary (문의 내용만) → 3줄 요약 (실패하면 직접 입력)
  → 회신 번호 입력 → POST /api/tickets/proxy (처리 시간 기록)
```

**흐름 C (담당자)**
```
담당자 선택 → GET /api/tickets?staffId=&status=open → [처리 완료] → PATCH /api/tickets/[id]
```

## 3. 데이터 모델

### 3.3 샘플 데이터 (`data/seed.ts`)

날짜는 **서버가 뜬 날(한국 시간)** 기준으로 계산해서 넣어요. 그래야 언제 시연해도 "지금 부재 중"인 담당자가 있어요.

| 담당자 | 지역 | 부재 일정 (오늘 = D) | 시험하는 규칙 |
|---|---|---|---|
| S01 김가온 | 창녕군 | D-1 ~ 이번 주 금요일 연차 + 다음 주 월~화 출장 | 주말을 사이에 둔 부재 이어 보기 → "다음 주 화요일까지" |
| S02 이나래 | 창녕군 | 없음 | 부재 아님 → 바로 연결 |
| S03 박도윤 | 진해구 | D-3 ~ 미정 (병가) | 복귀일 미정 문구 |
| S04 최서진 | 진해구 | D+7 ~ D+8 교육 | 오늘은 부재 아님 |

- **오늘이 토·일요일이면:** "이번 주 금요일"이 지나 있어서, S01의 첫 부재를 D-1 ~ D+2로 바꿔요.
- **고객 20명 (가상):**
  - 동명이인 2쌍: 이름과 끝 4자리가 같고 생년월일이 달라요 → 생년월일로 좁혀져요.
  - 이름·끝 4자리·생년월일이 모두 같은 1쌍 → "담당자 확인 필요"가 나와요.
  - 물건 6건을 가진 고객 1명 → 최대 5건 규칙을 시험해요.
  - 물건이 없는 고객 1명 → "연결된 물건이 없습니다"가 나와요.
- **물건 30건:** 담당자별 7~8건이에요.
- **공휴일 (`data/holidays.ts`):** 2026~2027년 대한민국 공휴일 목록이에요. 대체공휴일도 넣어요.

## 4. 규칙 함수 (`lib/rules/`): AI 없음

### 4.1 부재 판단 (`absence.ts`, FR-05)

```
입력: 담당자의 부재 일정 목록, 오늘(한국 시간)
1. 오늘을 포함하는 부재가 없으면 → 부재 아님
2. 있으면 그 부재의 종료일부터 시작해서 반복:
   - 종료일이 null → "복귀일 미정"으로 끝
   - 종료일 다음 날부터 다음 부재 시작일 전날까지가 모두 토·일·공휴일이면 → 이어진 부재로 보고 종료일을 늘림
   - 아니면 그 종료일이 "마지막 날짜"
출력: { absent: false } | { absent: true, until: "YYYY-MM-DD" } | { absent: true, until: null }
```

### 4.2 부재 안내 문구 (`notice.ts`, FR-06)

고정 문구에 이름·날짜만 끼워요. 2문장, 80자 이내예요.

| 경우 | 문구 |
|---|---|
| 복귀일 있음 | `{이름} 담당자는 {M}월 {D}일까지 부재 예정입니다. 회신 예약 또는 다른 직원 연결을 선택해 주세요.` |
| 복귀일 미정 | `{이름} 담당자는 현재 부재 중입니다. 복귀 일정은 확인 후 안내드리겠습니다.` (PRD 규칙 5 그대로) |
| 부재 아님 | 문구 없음 → "담당자에게 연결됩니다" 표시 |

- 시험에서 확인할 것: 문구가 80자를 넘지 않는지, 사유 단어(연차·교육·출장·병가)가 들어가지 않는지.

### 4.3 고객 찾기 (`lookup.ts`, FR-09)

```
입력: 이름, 끝 4자리, (선택) 생년월일 6자리
이름은 앞뒤·가운데 공백을 지우고 비교해요. 비슷한 이름은 찾지 않아요.

A = 이름 + 끝 4자리가 모두 같은 고객
- A가 1명 → found
- A가 2명 이상:
    생년월일 없음 → ambiguous (생년월일을 물어요)
    생년월일 있음 → A 중 생년월일 같은 고객: 1명 found / 2명 이상 needs-check / 0명 none
- A가 0명:
    생년월일 없음 → none (생년월일로 다시 찾기를 안내해요)
    생년월일 있음 → B = 이름 + 생년월일이 같은 고객: 1명 found / 2명 이상 needs-check / 0명 none
found일 때: 그 고객의 물건을 번호 순으로 최대 5건
```

### 4.4 회신 예약 합치기 (`merge.ts`, FR-08)

- 같은 `staffId`이고, 같은 고객(공백 지운 이름 + 끝 4자리)이며, `type: callback`, `status: open`인 건이 있으면 새로 만들지 않아요.
- 합칠 때:
  - `contactCount`를 1 올려요.
  - `updatedAt`을 바꿔요.
  - 새 문의 한 줄이 있으면 기존 내용 뒤에 ` / `로 붙여요. 전체는 300자까지예요.
  - 회신 번호가 다르면 새 번호로 바꿔요.

### 4.5 입력 검사 (`validate.ts`, FR-04·08·11)

| 칸 | 규칙 | 오류 문구 |
|---|---|---|
| 이름 | 공백 제외 1~20자 | 이름을 적어 주세요 |
| 끝 4자리 | 숫자 4개 | 전화번호 끝 4자리는 숫자 4개로 적어 주세요 |
| 생년월일 | 숫자 6개 + 실제 있는 날짜 | 생년월일은 6자리(예: 450312)로 적어 주세요 |
| 회신 번호 | 숫자와 하이픈, 숫자 9~11개, 0으로 시작 | 회신 번호를 확인해 주세요 |
| 문의 한 줄 | 100자 이내 | 100자 이내로 적어 주세요 |
| 문의 내용 | 1~1000자 | 문의 내용을 적어 주세요 |
| 요약 | 3줄, 줄마다 1~150자 | 요약 3줄을 모두 채워 주세요 |

**개인정보 형태 막기**: 문의 한 줄, 문의 내용, 요약에 적용해요.
- 휴대전화·일반전화 전체 형태: `0`으로 시작하는 9~11자리 숫자(하이픈·공백 허용)
- 주민등록번호 형태: 숫자 6개 + (하이픈·공백) + 1~8로 시작하는 숫자 7개
- 걸리면 `PERSONAL_INFO` 오류: "전화번호 전체나 주민등록번호는 적지 말아 주세요"

## 5. 서버 API (`app/api/`)

`/api/session`을 뺀 모든 API는 접근 코드 쿠키가 있어야 하고, 없으면 `401`이에요.

### 5.1 목록

| 메서드 | 주소 | 설명 | 요구사항 |
|---|---|---|---|
| POST | `/api/session` | 접근 코드 확인 → 쿠키 발급 | FR-02 |
| GET | `/api/staff` | 담당자 + 부재 상태 + 안내 문구 (사유 없음) | FR-05·06·07 |
| POST | `/api/calls` | 전화 흉내 화면의 선택 기록 | FR-07, FR-15 |
| POST | `/api/tickets/callback` | 회신 예약 (중복 합치기) | FR-08 |
| POST | `/api/lookup` | 고객 찾기 | FR-09·10 |
| POST | `/api/summary` | 문의 3줄 요약 | FR-12 |
| POST | `/api/tickets/proxy` | 대리응대 저장 | FR-11·13 |
| GET / PATCH | `/api/tickets`, `/api/tickets/[id]` | 담당자 목록 / 처리 완료 | FR-14 |
| GET | `/api/metrics` | 지표 | FR-15 |

### 5.2 상세

**`GET /api/staff`** → `200`
```json
{ "staff": [
  { "id": "S01", "name": "김가온", "team": "국유재산관리1팀", "region": "창녕군",
    "absent": true, "until": "2026-11-03",
    "notice": "김가온 담당자는 11월 3일까지 부재 예정입니다. 회신 예약 또는 다른 직원 연결을 선택해 주세요." }
], "regions": ["창녕군", "진해구"] }
```
- 응답 어디에도 `reason`이 없어요. 시험에서 문자열 검색으로 확인해요.

**`POST /api/lookup`**
- 요청: `{ "lookupId": "…", "name": "홍길순", "last4": "1234", "birth6": "450312"(선택) }`
- 응답 `200`:
```json
{ "result": "found", "customer": { "id": "C03", "name": "홍길순", "last4": "1234" },
  "properties": [{ "id": "P004", "address": "…", "landCategory": "전", "areaM2": 330, "status": "대부중", "staffName": "김가온" }],
  "moreProperties": 1 }
```
- `result`가 `ambiguous`·`none`·`needs-check`이면 `customer`와 `properties`가 없어요.
- 응답에 `birth6`는 **절대 넣지 않아요.**
- 같은 `lookupId`의 마지막 결과를 `LookupLog`에 남겨요.

**`POST /api/summary`**
- 요청: `{ "content": "…" }`. 이름·번호·생년월일 칸은 없어요.
- 처리 순서:
  1. 개인정보 형태를 검사해요.
  2. OpenAI를 불러요. 모델 `gpt-4o-mini`, 온도 0.1, JSON 응답, 15초 시간 제한이에요.
  3. 3줄을 붙여요.
- 응답 `200`: `{ "summary": "고객 요청: …\n확인된 사항: …\n담당자가 할 일: …" }`
- 실패하면 `502 AI_FAILED`예요. 화면은 직접 쓰기 칸을 열어요.

**`POST /api/tickets/proxy`** → `201 { "id": "…", "elapsedSeconds": 84 }`
- 요청: `{ staffId, lookupId, customerId, customerStatus, propertyIds, customerName, phoneLast4, callbackNumber, content, summaryAi, summary, startedAt }`
- 서버에서 다시 검사해요:
  - `customerId`가 있으면 그 `lookupId`의 결과가 `found`였고 같은 고객이어야 해요.
  - `propertyIds`는 그 고객의 물건이어야 해요.
  - 입력 규칙은 4.5를 따라요.

**`POST /api/tickets/callback`** → `201 { "id": "…", "merged": false }` 또는 `200 { "id": "…", "merged": true, "contactCount": 2 }`

**`GET /api/tickets?staffId=S01&status=open`** → `200 { "tickets": [...], "counts": { "open": 3, "done": 5 } }`
- 최신순으로 줘요. 생년월일은 들어 있지 않아요(애초에 Ticket에 없음).

**`GET /api/metrics`** → `200`
```json
{ "today": "2026-10-28",
  "proxyCount": 3, "avgSeconds": 96, "todaySeconds": 288,
  "lookupSuccessRate": 0.92, "blankCount": 0,
  "callChoices": { "callback": 6, "connect": 2, "notAbsent": 4 } }
```
- 셈 방법은 계획서 3.2를 따라요:
  - `proxyCount`(하루 대리응대 건수) = 오늘 `connect` 선택 수 + 오늘 `proxy` 저장 수 중 **큰 값**. 같은 통화가 두 번 세지지 않게 해요.
  - `lookupSuccessRate` = `found` ÷ 전체 lookupId 수

## 6. AI 지시문 (요약 1곳)

```
당신은 국유재산 담당 부서에서 부재 중인 동료에게 전화 문의를 전달하는 메모를 쓰는 직원입니다.
아래 [문의 내용]만 근거로 3가지를 한국어 존댓말 한 문장씩(각 150자 이내)으로 쓰세요.
- request: 고객이 원하는 것
- confirmed: 통화에서 확인된 사실 (없으면 "확인 필요")
- todo: 담당자가 복귀 후 할 일
규칙:
1. [문의 내용]에 없는 사실(금액, 날짜, 약속, 법령)을 추가하지 마세요.
2. 불확실하면 "확인 필요"라고 쓰세요.
3. 전화번호, 주민등록번호, 사람 이름은 쓰지 마세요.
JSON으로만 답하세요: {"request": "...", "confirmed": "...", "todo": "..."}
```

- 서버가 세 칸을 "고객 요청: / 확인된 사항: / 담당자가 할 일:"로 붙여요. 빈 칸은 "확인 필요"로 채워요.
- 결과에도 개인정보 형태 검사를 한 번 더 해서, 걸리면 그 줄을 "확인 필요"로 바꿔요.
- **시험 모드:** 이 작업 공간에서는 OpenAI에 접속할 수 없어요. 그래서 `.env.local`의 `AI_STUB=1`일 때 정해진 시험용 요약을 돌려줘요. Vercel에는 넣지 않아요.

## 8. 오류 처리

### 8.1 오류 코드

| 코드 | 상태 | 뜻 | 화면 문구 |
|---|:-:|---|---|
| `UNAUTHORIZED` | 401 | 접근 코드 없음/틀림 | 접근 코드가 맞지 않아요 |
| `VALIDATION` | 400 | 입력 형식 오류 | 4.5의 칸별 문구 |
| `PERSONAL_INFO` | 400 | 전화번호 전체·주민번호 형태 | 전화번호 전체나 주민등록번호는 적지 말아 주세요 |
| `NOT_FOUND` | 404 | 없는 담당자·건 | 찾을 수 없어요 |
| `CONFLICT` | 409 | 저장 요청이 찾기 결과와 다름 | 고객 찾기를 다시 해 주세요 |
| `AI_FAILED` | 502 | 요약 실패·15초 초과 | AI 요약을 받지 못했어요. 직접 3줄을 적어 주세요 |
| `CONFIG` | 500 | `APP_ACCESS_CODE`·`OPENAI_API_KEY` 없음 | 서버 설정이 필요해요. 관리자에게 알려 주세요 |

{ "error": { "code": "VALIDATION", "message": "전화번호 끝 4자리는 숫자 4개로 적어 주세요", "field": "last4" } }

## 9. 보안

- **접근 코드 (`proxy.ts` + `lib/access.ts`):**
  - Next.js 16은 `middleware` 대신 `proxy`를 쓰고, Node.js 환경에서 돌아요.
  - `/login`, `/api/session`, 정적 파일을 뺀 모든 요청을 검사해요.
  - 쿠키는 `APP_ACCESS_CODE`로 서명한 값(HMAC-SHA256, `node:crypto`)이에요. 설정은 `httpOnly`, `secure`, `sameSite=lax`, 12시간이에요.
  - 쿠키가 없을 때 화면 요청은 `/login`으로 보내고, API 요청은 `401`을 돌려줘요.
  - 코드 비교는 길이 차이로 정보가 새지 않는 방식(`timingSafeEqual`)으로 해요.
- **비밀 값:** `OPENAI_API_KEY`, `APP_ACCESS_CODE`는 `lib/` 서버 파일에서만 읽어요(`import "server-only"` 대신 서버 파일에서만 읽는 규칙으로 지켜요. 새 라이브러리 추가 금지).
- **개인정보:**
  - 생년월일은 서버 안에서 비교에만 쓰고, 어떤 응답에도 넣지 않아요.
  - AI에는 문의 내용만 보내요.
  - 개인정보 형태는 화면과 서버 양쪽에서 막아요.
- **부재 사유:** `Absence.reason`은 `lib/store.ts` 밖으로 내보내는 함수가 없게 만들어요.
- **입력 길이:** 4.5의 제한을 서버에서 다시 적용해요.
